1 — Introduction

Mission Control allows you to visualize the procedure of your transformation project and ensure that you take the right steps at the right time. The software allows you to plan, control and monitor the entire transformation process.

The procedure you depict provides options for integrating various software components, maintaining dependencies and documenting tasks. You can execute the steps within the procedure manually or automatically.

Licensing

You must license newly created projects. Without a license, you can adjust the project plan, but cannot execute tasks. Contact SNP Support for more information.

Training

SNP recommends a training course for this software — at their training center or on your premises. See snpgroup.com/en/snp-academy

Copyright

Mission Control and all related documentation are the intellectual property of SNP Schneider-Neureither & Partner SE.

1.2 Requesting SNP Support Services

You can request SNP Support services via the SNP Support Portal at support.snpgroup.com. If you do not have a user yet, register a new user as explained below.

1.2.1 Requesting Support

  1. Open the SNP Support Portal.
  2. Log in with your user data.
  3. In the Service Desk Requests area, click Request Standard Support.
  4. Fill out all the required fields. The more information you provide, the more precisely the problem can be analyzed.
  5. In the Help from SNPedia area, click Start SNPedia Search. The Search Result(s) window opens with suggested solutions.
  6. If none of the solutions match, click Continue with ticket.
  7. Optional: Add attachments.
  8. In the Priority and Descriptions area, define the priority and add a description.
  9. Click OK – Apply changes and close at the bottom right.
You have created a ticket and requested support.

1.2.2 Registering Users

  1. Optional: Ask another SNP Support Portal user to create a new user by clicking Register New User for Customer in the Service Desk Requests area. Provide all required information and confirm by clicking OK – Apply changes and close.
  2. Optional: Ask your SNP contact to create a new user.
  3. You will receive an e-mail with a password. Follow the instructions and complete the registration.

1.3 Creating a User for a Customer in the SNP Support Portal

1.3.1 Creating a User

  1. Open the Support Portal at https://support.snpgroup.com/.
  2. Click the tile Register new user for customers.
  3. Click the plus icon (yellow) to select the project. Alternatively, disable project selection (green) if the project is unknown, missing or not yet created.
  4. Enter all required information: Business partner details, New user details, Request details (SAP project number or SAP customer number if needed).
  5. Click to open the ticket.

1.3.2 Informing the Requesting Person

Inform the user that you have initiated the registration (reference the document Requesting SNP Support Services). You will be informed as soon as the new user is created.

4.3.2 Maintaining Variables — Steps

  1. Start transaction /N/SNP/MC.
  2. Optional: Select a project.
  3. Click Design mode.
  4. Go to the Variables tab.
  5. Click Add variable.
  6. Assign a name.
  7. Optional: Enter a description.
  8. Optional: Define the variable type: DDIC type (from ABAP Data Dictionary), Native type (Data type + Length), or Range type (transforms scalar to selection list).
  9. Optional: Click Change default value and enter a default value.
  10. Optional: Specify a Reference domain and Reference system for value help and value check.
  11. Optional: Set Scope type for modularization: INPUT (filled outside, used inside), OUTPUT (filled inside, used outside), LOCAL (only within module).
  12. Optional: Specify a Validator class (must implement /SNP/CN01_IF_TASK_VARIABLE_VAL).
  13. Optional: Enter a Value help class (must implement /SNP/CN02_IF_TASK_VARIABLE_VH).
  14. Enable Transfer runtime value to copy the runtime value when copying the task.
  15. Click Save.

4.3.3 Allowing Users to Maintain Variable Values

Configure a task to provide users with a form pop-up using the class /SNP/CN02_CL_TEX_EDIT_VARIABLE:

<config R:CLASS="/SNP/CN02_CL_TEX_EDIT_VARIABLE" R:REMOTE_CALLTYPE="LS"
        R:IV_VARIABLES="VAR1,VAR2,VAR3*,VAR4.FIELD1">
  <FORM_CONFIG NAME="VAR1" CAPTION="{M:GET_TEXT Caption}" REQUIRED="X" />
  <FORM_CONFIG NAME="VAR2" CAPTION="{M:GET_TEXT Another caption}" REQUIRED="" />
</config>
Specify variables as comma-separated list. Use patterns (VAR3*) and dot notation (VAR4.FIELD1) for field access.

10.6 Mapping — Architecture, Types & Examples

Mapping is the transformation brain of CrystalBridge. It defines precisely how every value extracted from the source system is translated before being loaded into the target system. Mapping operates at multiple levels — from simple 1:1 value replacement to complex ABAP-driven derivation logic — and is applied between the Export and Import blocks during the staging phase.

10.6.1 Mapping Architecture

SOURCE SYSTEM (ECC/R3)
  Raw SAP Data: BUKRS=1000, KOKRS=CO01, PRCTR=PC100, KUNNR=0000012345, WAERS=USD
        |
        | EXPORT BLOCK
        v
  STAGING AREA  (Intermediate Layer - raw data stored here)
        |
        | MAPPING ENGINE applies:
        |  Value Mapping    : BUKRS 1000 --> 2000
        |  Field Mapping    : KUNNR --> PARTNER (S/4HANA BP)
        |  Derivation Rule  : PRCTR derived from KOSTL
        |  Hard-Coded Value : LOGSYS always = S4HPRD100
        |  Default Value    : GSBER empty --> 0001
        |  Conditional Map  : IF WAERS=USD THEN EUR
        v
  TRANSFORMED DATA  BUKRS=2000, KOKRS=CO02, PRCTR=PC200, PARTNER=0000012345, WAERS=EUR
        |
        | IMPORT BLOCK
        v
TARGET SYSTEM (S/4HANA / New ECC)
  Final SAP Data: BUKRS=2000, KOKRS=CO02, WAERS=EUR
Mapping rules are defined in the TC scenario and evaluated at transformation time. The source system data is never modified.

10.6.2 The Three Mapping Layers

LayerScopeDescription
Global MappingScenario-wideApplies to ALL data objects. Example: BUKRS 1000 to 2000 applied everywhere in the scenario.
Object-Level MappingSingle data objectOverrides or extends global mapping for one object. Example: FI documents use a different GL account mapping than MM objects.
Field-Level MappingSingle table fieldFine-grained rule on a specific field within a specific table. Example: BSEG field KOSTL uses custom derivation logic.

10.6.9 Mapping Best Practices

  • Start with org-unit mappings first — BUKRS, KOKRS, WERKS, VKORG are referenced in almost every data object
  • Use bulk import for large mapping tables — manually entering 500+ GL account mappings is error-prone; use CSV import
  • Validate after every change — run /SNP/TE02_VALIDATE_MAPPINGS before each test run, not just before go-live
  • Document all derivation rules — complex ABAP derivations are hard to debug; keep a mapping specification aligned with the TC config
  • Test with simulation mode first — execute blocks in simulation mode to verify mapping output without writing to target
  • Use Mission Control variables — store key values (e.g. target company code) as MC variables so they can be reused across tasks without hardcoding
  • Business user sign-off — have functional owners confirm all value mappings before go-live; use role /SNP/TF_TC_TC_700_DIA_BUSI for controlled access

10.14 Near-Zero Downtime (RBNZD)

Rule-Based Near-Zero Downtime (RBNZD) minimizes system downtime during migration by allowing the source system to remain live while the bulk of data is migrated in advance. Only the final delta (changes since the last run) is migrated during the cutover window.

10.14.1 RBNZD Approach

PhaseDescription
1 — Initial LoadFull data extraction and import while source is live. Source users continue working.
2 — Delta SyncMultiple delta runs to sync changes. Can be repeated to minimize final delta size.
3 — Final DeltaShort downtime window — final delta migration. Source locked, final sync, target go-live.

  1. Assign role /SNP/TF_DO_RBNZD_700_DIA_ALL.

  6. Create delta loads using /SNP/ZD02_MC_CREATE_DELTA_LOAD.

10.15 Delta Load

Delta loads transfer only data changed since the last run. This is the core mechanism for keeping the target system synchronized with the source during a migration project.

10.15.1 Delta Load Process

  1. Initial full load must be completed first.
  2. The system records a delta timestamp after each successful export.
  3. On the next delta run, only records created or changed after the delta timestamp are extracted.
  4. Delta imports are applied to the target system on top of the existing data (update mode).

10.15.2 Creating and Executing Delta Loads

  1. Create a delta load configuration using /SNP/ZD02_MC_CREATE_DELTA_LOAD.
  2. In Mission Control, add an automated task with execution class /SNP/ZD01_CL_MC_EXECUTE_TASK.
  3. Configure the delta run parameters (scenario, run name, delta timestamp handling).
  4. Execute the task from Mission Control.
  5. Monitor progress via the Task Daemon or refresh class /SNP/TE02_CL_TEX_TR_REFRESH.

10.15.3 Delta Load Best Practices

  • Run deltas frequently (daily or more) to minimize the final cutover delta size.
  • Validate each delta run with DCV before proceeding to the next.
  • Lock number ranges on the target before each delta import and unlock after.
  • Track delta timestamps carefully — avoid overlap or gaps.
  • Test the full delta process (including rollback) in the QA environment before production.

  7. After data record processing

  10. After table processing
  11. After data object export

11.11.1 Address Object

Address data (domains ADRNR, AD_ADDRNUM, AD_PERSNUM, AD_SO_KEY, CADRNR) is handled by a special address object. Address numbers are collected by global export rules and stored in global selection SEL_ADRNR. The ADR object must be exported last and imported first.

11.11.2 Creating Transformation Runs and Blocks

Blocks are assigned a type and contain data objects:

11.11.4 Run Steering and Daemon

The TC Daemon is a background SLEEP process (/SNP/TE01_DAEMON, visible in SM50) that:

  • Monitors all running executions (status, record counts, log entries from satellite systems)
  • Only affects the timeliness of cockpit display — does not drive the actual execution except for dependency-based starts
  • Standard daemon cycle: up to 5 seconds

Manual run steering: Reset, Refresh, Stop, Restart, Duplicate at Run / Block / Data Object / Table levels.

11.11.5 Managing Export Files

  • Files are created per export run and never overwritten
  • Deleting a block also deletes its associated files
  • Import uses the last exported file by default; can be manually re-assigned via context menu
  • For multiple source systems, import blocks must be manually assigned to export blocks

11.12 Data Validation

11.12.1 Compare Export to Target Content

After import, compare export file contents against the target table. Key fields must be identical. Changed non-key fields (mapped values) are shown as differences — this is expected.

11.12.2 Test Units

11.12.3 Data Consistency Verification (DCV)

An ABAP-based check report invoked via:

  • Data Objects or Transformation area: SAP Menu → Functions → SNP Foreign Key Check
  • Transaction /N/SNP/FKC on the target system

Supports SAP ERP, HCM, and S/4HANA. Check types:

  • Domain fixed value check (table DD07L)
  • Foreign key & value table check (SE16 column check table / Remote SE16)

Prerequisites: Migration complete, check tables filled. Assign field statuses to categorize results and assign table contexts (priority, responsibility, ownership).

Results output: aggregated by checks, by tables, by domains; comparison of two transactions (before/after conversion or before/after cross-release migration).

11.12.4 Automated Testing for Transformation Scope

Tests execute at application level via SAP GUI in read and change mode. Flow: Selection → TC Transformation Import → Random selection → Check → Evaluation/Result. Supports individual checks, system checks, and selected test data.
