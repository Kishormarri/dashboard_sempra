Before You Start — What Is Changing and Why

Understand the change in one minute before touching any tool

CONCEPT
ECC has two separate objects. S/4HANA has one.
Customer (KNA1) + Vendor (LFA1) → Business Partner (BUT000)

In ECC, a Customer and a Vendor are completely separate — even if they are the same real company. In S/4HANA they collapse into one Business Partner (BP) record with roles attached.

ECC Customer
KNA1 · KNB1 · KNVV
+
ECC Vendor
LFA1 · LFB1 · LFM1
→
S/4 Business Partner
BUT000 + BP Roles
Real example — Siemens AG In ECC: Customer 100045 (they buy from us) AND Vendor 200078 (we buy from them) — two separate records, no link between them.

In S/4HANA: ONE Business Partner BP# 100045 with roles FLCU00 (customer-general), FLCU01 (customer-CoCode), FLVN00 (vendor-general), FLVN01 (vendor-CoCode).

A/R posts via Customer 100045 → routed to BP 100045. A/P posts via Vendor 200078 → also routed to BP 100045. Treasury sees the net exposure in one place.

FLCU00Customer — general dataKNA1Name=Siemens AG, Country=DE
FLCU01Customer — per company codeKNB1Recon acct 140000, terms Z030
FLVN00Vendor — general dataLFA1Name=Siemens AG (same record)
FLVN01Vendor — per company codeLFB1Recon acct 210000, pay method T

The CVI link CVI (Customer-Vendor Integration) keeps KNA1, KNB1, LFA1, LFB1 alive in S/4 and in sync with BUT000. Old T-codes like XD01 and XK01 still work — they redirect through CVI to the BP screen. The migration must create CVI_CUST_LINK and CVI_VEND_LINK rows for every record.

  • Export — SNP reads KNA1, KNB1, KNVV, LFA1, LFB1, LFM1 from ECC. Nothing in ECC is ever changed.

Phase 1 — Prepare the Data

Do this before opening any SNP tool. Fix problems in the source, not mid-migration.

STEP 1
Profile the customer and vendor master data
Find blanks, duplicates and invalid values in KNA1 and LFA1 before extraction

Run SE16N on KNA1 and LFA1 in ECC. Check for:

  • Blank NAME1 — name cannot be blank; BP creation will fail
  • Invalid LAND1 — country must exist in table T005
  • Missing KTOKD / KTOKK — account group drives BP grouping and number range
  • Missing SPRAS — language key must exist in T002
Example check SE16N on KNA1 → filter NAME1 = ' ' (blank). Any rows returned = those customers will fail BP creation. Fix in ECC before the first export.
STEP 2
Find customers who are also vendors (dual-role)
These must become ONE BP — most complex scenario, plan early

Use SNP tool /N/SNP/CW_MDA to compare KNA1 and LFA1. Match on STCD1 (tax number) or NAME1 + LAND1.

Real example — dual-role detection KNA1-STCD1 = 'DE123456789' on Customer 100045 AND LFA1-STCD1 = 'DE123456789' on Vendor 200078 → same company.
Decision: use Customer# as BP#. Result: BP 100045 gets all four roles: FLCU00 + FLCU01 + FLVN00 + FLVN01. Vendor 200078 links to BP 100045 via CVI_VEND_LINK.
Needs Professional Services Dual-role harmonisation is NOT an out-of-the-box SNP unit. Identify all cases before design phase — cannot be fixed easily after go-live.
STEP 3
Convert bank account numbers to IBAN
ECC stores BANKN — S/4HANA requires IBAN. Must convert before migration.
  • Run SAP program RFFMIBAN — converts KNBK/LFBK BANKN → IBAN for all records
  • Manually fix any records RFFMIBAN cannot convert
  • Ensure all bank keys (BANKL) exist in BNKA with a BIC code
Before and after ECC LFBK: BANKS=DE, BANKL=37040044, BANKN=0532013000
S/4 TIBAN: IBAN = DE89 3704 0044 0532 0130 00
If IBAN conversion is skipped Every F110 payment run and every direct debit fails on day one. There is no quick fix — all bank records must be re-loaded.
STEP 4
Validate reconciliation accounts exist in S/4HANA
KNB1-AKONT (type D) and LFB1-AKONT (type K) must exist on target before import
  • Customer recon accounts: type D in SKA1 (e.g. account 140000)
  • Vendor recon accounts: type K in SKA1 (e.g. account 210000)
  • Check in S/4: SE16N → SKA1 → KTOPL = your chart of accounts → SAKNR = 140000 → verify KTOKS = D
  • If missing: create in S/4 with FS00 before running the BP import

Overlap check — before go-live SE16N on BUT000 — confirm no PARTNER value exists in both KNA1 (KUNNR) and LFA1 (LIFNR). Any overlap = those records must be merged into one BP before migration.
STEP 6
Configure BP Groupings and Roles (BUCF)
Groupings link account groups to ranges. Roles activate master data screens.
  • Create groupings: CUST, VEND, CPD, INTE — assign each to its number range
  • Verify BP Roles exist: FLCU00, FLCU01 (customer), FLVN00, FLVN01 (vendor)
  • Assign each role to its BP Role Category: FLCU = Customer category, FLVN = Vendor category
  • Set field status per role: STCD1 = Required for FLCU00; ZWELS = Required for FLVN01
Example OBD2: Customer account group KUNA (range 1000–1999999) → BP grouping CUST
OBD3: Vendor account group 0001 (domestic) → BP grouping VEND
STEP 7
Map account groups to BP roles in CVI (SPRO)
SPRO → Cross-Application → Master Data Synchronization → Customer/Vendor Integration
  • CVI → Customer → Assign Roles: account group KUNA → roles FLCU00 + FLCU01
  • CVI → Vendor → Assign Roles: account group 0001 → roles FLVN00 + FLVN01
  • CVI → Number Range Mapping: link KUNNR range to BP external range (keeps ECC numbers)

Configure CVI field mapping (KNA1 / LFA1 → BUT000)

Phase 3 — Set Up the SNP TC Scenario

Build the migration blueprint in the Transformation Cockpit (/N/SNP/TC) on the control system.

STEP 10
Create the Bluefield scenario (Scenario Configurator — 5 steps)
/N/SNP/TC → /SNP/TE02_SCEN_CONFIGURATOR
  • Step 1 — Add file: upload SNP_MIG* template (delivery content uploaded manually at project start)
  • Step 2 — Scoping: select Bluefield type; enter Scenario ID (max 30 chars, e.g. BP_ECC_S4_BLUE)
  • Step 3 — Target system: assign S/4HANA target; set parameters TGT_SYS_CREA_TYPE_TC, TGT_S4CORE_VERSN
  • Step 4 — Import preview: review what will be created
  • Step 5 — Cleanup: confirm and finish
Result Scenario ID: BP_ECC_S4_BLUE stored as Mission Control variable TC_SCENARIO. Every MC task reads {M:GET_VARIABLE TC_SCENARIO} to know which scenario to run.
STEP 11
Assign systems and test all RFC connections
Systems tab → add source ECC + target S/4 → test connections
  • Add source system: alias ECC, role SOURCE, RFC destination to ECC
  • Add target system: alias S4H, role TARGET, RFC destination to S/4HANA
  • Test all connections: /SNP/TE02_API_CHECK_SYS_CONS — all must be green
  • Check file paths: /SNP/TE02_API_CHECK_FILE_PATHS — share accessible from all systems
Never rename the system alias after setup The alias is embedded in global selection values. Renaming it breaks all selection maintenance already done.
STEP 12
Run Table Analysis on all BP tables
/SNP/TE02_UPDATE_TABLE_INFO — mandatory before any data object can run

Table Analysis scans source and target — collects DDIC structure and record counts into /SNP/CE00TABINFO. Without this the cockpit refuses to process any data object.

Run on: KNA1, KNB1, KNVV, KNVP, LFA1, LFB1, LFM1, ADRC, BUT000, TIBAN — and re-run after any transport that changes table structures.

STEP 13
Define global selections — what scope moves
Selections tab → one global selection applies to every table with that field domain
SelectionDomainExample valuesMeaning

Two silent traps — check before every export (1) Global selection with NO values → zero records transferred — looks like it ran fine.
(2) Field selection on one table with NO value → the entire table is exported — too much data.
Always run /SNP/TE02_SELECTION_OVERVIEW and check for empties before Export.
STEP 14
Set up mapping — what changes on the way in
Mapping tab → activate objects → enter source / target values → validate → regenerate blocks

Mapping is applied between export and import. The source file stays raw. Only the target gets the new values.

After entering all values: run /SNP/TE02_VALIDATE_MAPPINGS → fix all gaps → regenerate blocks with /SNP/TE02_API_CREATE_BLOCKS. New mapping entries are NOT used until blocks are regenerated.

Phase 4 — Pre-Execution Checks

Run all of these before pressing Execute. Errors found now cost minutes; errors mid-run cost hours.

STEP 17
Run the 8 pre-execution validation checks — all must pass
0 errors on all checks before the first export starts
  • ✓
    /SNP/TE02_API_CHECK_SYS_CONS — all RFC connections green
  • ✓
    /SNP/TE02_VALIDATE_SELECTIONS — no empty global selections, no orphan field selections
  • ✓
    /SNP/TE02_VALIDATE_MAPPINGS — every KUNNR, LIFNR, BUKRS source value has a target
  • ✓
    /SNP/TE02_VALIDATE_OBJECTS — all data objects valid
  • ✓
    /SNP/TE02_API_REMOTE_DDIC_ANA — DDIC matches source and target
  • ✓
    /SNP/TE02_API_EXEC_SYNTAX_CHK — 0 syntax errors (transform terminates on any error)
  • ✓
    /SNP/TE02_API_VIOLATION_CHECK — referential integrity and mandatory fields clean
  • ✓
    Role /SNP/XX_MIG_BAPI_SAT_700_ALL assigned on S/4 target (separately installed — BP BAPI will fail without it)
STEP 18
Simulate the import block before the first real run
Block → Execute → Simulation mode — writes nothing, checks for duplicates and key conflicts
Example — what simulation catches Simulation on BLK_CUST_IMP reports: "Duplicate key on BUT000-PARTNER 1001234." BP 1001234 already exists from a previous test load. Fix: reset the target QA system before the next mock cycle.
Simulation cannot start once a real import has run on that block. Always simulate before the first real run of each block.

Phase 5 — Execute and Test (Mock Cycles)

Run at least two full mock loads in QA before touching production.

STEP 19
Run the export block — reads ECC, writes packages
MC Task 1 → EXP block → KNA1, KNB1, KNVV, LFA1, LFB1, LFM1 extracted to file share
  • Scout Reader reads KNA1 → then KNB1 (FOR ALL ENTRIES on KNA1 export) → then KNVV, etc.
  • Packages written to: [share]/BP_ECC_S4_BLUE/BLK_CUST_EXP/KNA1/
  • Files are never overwritten — restart exports only failed tables
After export — count check Log tab: KNA1 = 45,000 records. Compare to SE16N on ECC source — must match the selection scope. KNB1 ≥ KNA1 (multiple CoC records per customer). If counts differ: check selection, connection key, or reader type.
STEP 20
Run the import block — writes to S/4HANA
MC Task 2 → IMP block → mapping applied → BUT000 written → BAPI creates BP roles
  • Mapping applied on the way in: BUKRS 1000→2000, KUNNR 1001234→BP 1001234, DEM→EUR
  • Import sequence: KNA1 written before KNB1, LFA1 before LFB1 (header always before item)
  • BAPI call creates BUT000 + assigns BP roles FLCU00/FLCU01 and/or FLVN00/FLVN01
After import — check Log tab: written = exported (minus records skipped by rules). Remote SE16 (/SNP/CN_SE16) on BUT000 — count should match KNA1 count.
If the block crashes mid-run 1. Read the log — find the error (e.g. "no target value for BUKRS=1200").
2. Fix the cause — add the missing mapping entry.
3. Regenerate blocks (/SNP/TE02_API_CREATE_BLOCKS).
4. Click Restart — continues from last good package. Do NOT click Reset unless you want full re-extraction from source.

STEP 22
Repeat mock cycles — minimum 2 full dress rehearsals
/SNP/TE02_API_COPY_RUNS_BLOCKS — copy runs for each new cycle
  • Copy existing runs: /SNP/TE02_API_COPY_RUNS_BLOCKS
  • Each cycle must pass ALL Step 21 checks before proceeding
  • Never carry known errors into the next cycle or into production

Phase 6 — Production Load & Cutover

Only after all mock cycles pass with 0 errors. Source stays live during initial load (Bluefield / RBNZD).

STEP 23
Lock NRIV → run production initial load → unlock → BUPT
Background mode via Mission Control — never dialog for production runs
  • Lock NRIV BP number ranges on S/4 target (prevents parallel BP creation conflicts)
  • Execute production initial load — background mode via MC (run as background job, never dialog)
  • Unlock NRIV immediately after import block completes
  • Run BUPT immediately — 0 errors gate before any delta runs start
STEP 24
Run RBNZD delta loads daily until cutover
Each delta shrinks the volume for the final cutover window
RunSource stateVolumeDowntimeAction
Initial loadLive100%NoneFull export + import of all BP scope
Delta 1Live~20%NoneNew/changed BPs since initial load; BUPT after
Delta 2Live~5%NoneChanges since delta 1; DCV + BUPT
Delta nLive~1–2%NoneRepeat until delta fits in cutover window
Final deltaLocked<1%ShortLock source → final delta → validate → go-live
  • Lock NRIV before every delta import; unlock after. DCV + BUPT after every delta.
  • Execute delta as MC task: /SNP/ZD01_CL_MC_EXECUTE_TASK
STEP 25
Final cutover delta → validate → go-live sign-off
Lock source → final delta → BUPT + test postings → all workstreams sign off
  • Lock ECC source (no new postings)
  • Run final delta — only records changed since last delta
  • Run BUPT (0 errors), CVI_CUST_LINK, CVI_VEND_LINK, DCV
  • Post test FI invoices (customer + vendor) — confirm A/R and A/P postings succeed
  • FI, SD, MM, Basis leads all sign the validation sheet
  • Go-live approved only when all of the above are green
7

Phase 7 — Post Go-Live

Activate CVI sync, run post-processing, monitor daily for 2 weeks.

STEP 26
Activate CVI bidirectional sync
SPRO → CVI → Activate (now live for ongoing use)

After go-live, any change to a BP syncs automatically to KNA1/LFA1 and vice versa. Users changing an address in the BP screen → appears in KNA1 automatically. Use CVI_CUST_CENTRAL / CVI_VEND_CENTRAL to force a resync if any drift is detected.

STEP 27
Run S/4HANA post-processing (XPRA · XCLA · SDM)
Adjusts migrated data to the S/4HANA data model
  • XPRA — post-processing routines adjusting migrated data structures
  • XCLA — classification and characteristic value assignments
  • SDM — Selective Data Migration programs for Finance and Logistics; requires role /SNP/TF_TC_PP_SAT_754_ALL (separately installed)
  • Authorization for post-processing: /SNP/TF_TC_PP_700_ALL
STEP 28
Hypercare — monitor BUPT daily for 2 weeks
Any new BP consistency error post go-live = immediate investigation
  • Run BUPT every morning for 2 weeks — any new error is investigated immediately
  • Monitor /SNP/TCPROT for anomalies in import logs
  • Run CVI_VEND_CENTRAL / CVI_CUST_CENTRAL if any sync drift is found
  • Close the MC project only after hypercare passes with 0 issues
