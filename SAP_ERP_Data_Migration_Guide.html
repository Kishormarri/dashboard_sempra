2 — SAP Migration Architecture & Best Methodologies

2A — End-to-End Migration Architecture

Every SAP data migration — regardless of size — follows the same five-layer architecture. Understanding all five layers prevents the #1 project failure mode: treating migration as a pure technical task rather than an integrated business + technical programme.

① Source Layer

Legacy system extraction — ERP, flat files, Access DB, Excel. Raw data in original format. ETL reads here.

② Staging Layer

Neutral landing zone — SQL Server, HANA, BODS datastores. Data cleansed, deduped, mapped, validated here. Never load direct from source.

③ Transform Layer

Business rule engine — value mapping, derivation, enrichment, format conversion. BODS transforms / ABAP conversion programs live here.

④ Load Layer

SAP target system. Data enters via BAPI / IDoc / LSMW / DMC / Direct Input. SAP business logic fires here — validations, number ranges, postings.

⑤ Reconciliation Layer

Verification gate. Count checks, value checks, spot checks, sign-off. No object is "done" until reconciled and approved by business owner.

Architecture Principle: The staging layer is non-negotiable. Never extract from legacy and load directly into SAP in one step. The staging layer is where data quality issues are found — not in SAP. Finding errors in SAP means re-running the entire load sequence.

2B — SAP Data Migration Project Methodology (5-Phase)

Phase 1 — Discover

Identify all source systems. Build object inventory. Assign business owners. Sign off migration scope document.

Phase 2 — Design

Field mapping design. Transformation rules. Architecture decisions (BODS vs LSMW vs BAPI). Data quality rules defined.

Phase 3 — Build

Extract programs. BODS jobs / LSMW programs. Mapping templates. Reconciliation reports. Error handling design.

Phase 4 — Mock

Mock Run 1 (dev) — all objects. Mock Run 2 (QA) — timed, full sequence. Mock 3 (pre-prod) — cutover rehearsal.

Phase 5 — Cutover

System freeze. Delta extract. Full load sequence. Reconcile. Go/No-Go. Go-Live. Hypercare 10 days.

LSMW Step Sequence (All Methods)
  1. Maintain Object Attributes — select object (e.g. 0050 = GL Accounts), method, program
  2. Maintain Source Structures — define the flat file columns (structure names + fields)
  3. Maintain Source Fields — describe each source column (length, type)
  4. Maintain Structure Relations — map source structure(s) to SAP target structure(s)
  5. Maintain Field Mapping and Conversion Rules — write conversion rules (hardcode, rule, ABAP code)
  6. Maintain Fixed Values, Translations, User-Defined Routines — value mappings (e.g. "DE" → "DE")
  7. Specify Files — set flat file path (local PC or application server)
  8. Assign Files — link source structure to the file
  9. Read Data — parse the flat file into LSMW internal tables
  10. Convert Data — apply all mapping rules; inspect conversion log for errors
  11. Create Batch Input Session / Start Direct Input — execute the actual load
  12. Run Batch Input Session (SM35) — if BDC method; foreground first, then background
Error Handling: After each run, check the spool (SP02) or SM35 session log for errors. Fix source data, re-run only error records. Never re-run all records — use LSMW restart capability to skip already-loaded records. Keep a log of each run attempt with timestamp and record count.

Step 1 — Open LSMW Transaction
  1. Log on to SAP ECC/S4 DEV client. Run transaction LSMW
  2. Click Create Project: Project = CUSTMIGR, Subproject = KUNA, Object = CUST_GEN
  3. Enter description: "Customer Master Migration — General + FI + SD Views"
  4. Press Enter to open the 12-step LSMW workbench screen
Naming convention: Project = migration wave (e.g. WAVE1), Subproject = object type (e.g. CUSTOMER), Object = sub-object (e.g. GENERAL, FIVIEW, SDVIEW). Keep them short — max 10 chars.
Step 2 — Maintain Object Attributes (Step 1 in LSMW)
  1. Double-click "Maintain Object Attributes" from the LSMW step list
  2. Set Object type = Business Object
  3. Set Object = CUSTOMER
  4. Set Method = CREATEFROMDATA1 → this maps to BAPI BAPI_CUSTOMER_CREATEFROMDATA1
  5. Click the blue ✔ (Save) button — do NOT press Enter as that navigates away
If you do not see "CUSTOMER / CREATEFROMDATA1" in the dropdown, the BAPI interface in your system may need activation. Run SE37 → search for BAPI_CUSTOMER_CREATEFROMDATA1 → confirm it exists. In some older ECC systems, use Object = 0070 (Customer) with method = Standard instead.
Step 3 — Maintain Source Structures (Step 2 in LSMW)
  1. Double-click "Maintain Source Structures"
  2. Click Create Source Structure → Name = HEADER, Description = "Customer CSV Row"
  3. This creates the flat structure that represents one row of your CSV file
  4. For complex objects (Customer has 3 views), you may optionally add sub-structures. For this BAPI method, a single flat structure works — the field mapping in step 5 will route fields to the correct BAPI parameter structures.

Step 5 — Maintain Structure Relations (Step 4 in LSMW)
  1. Double-click "Maintain Structure Relations"
  2. LSMW shows left pane (source structures) and right pane (BAPI target structures)
  3. The BAPI BAPI_CUSTOMER_CREATEFROMDATA1 exposes these target structures: PI_CENTRALDATA, PI_CENTRALDATAX, PI_COMPANYDATA, PI_COMPANYDATAX, PI_SALESDATA, PI_SALESDATAX
  4. Map source structure HEADER → to each of the target structures listed above (click and drag or use the "Assign" button)
  5. The X structures (e.g. PI_CENTRALDATAX) are "change flag" structures — they tell SAP which fields to update. You must set each X field = 'X' in the field mapping to activate that field.
BAPI method in LSMW uses change indicator structures. For every field you map a value to in PI_CENTRALDATA, you MUST also set the corresponding field in PI_CENTRALDATAX = 'X'. Otherwise SAP ignores the field even if a value is present. This is the #1 cause of "missing fields" in BAPI migrations.

Step 8 — Specify Files (Step 7 in LSMW)
  1. Double-click "Specify Files"
  2. Select File on PC (local) for testing; switch to File on Application Server for production runs
  3. File name: C:\migration\customers.csv (for local) or /usr/sap/migration/customers.csv (app server)
  4. Set Field separator: , (comma)
  5. Set Header rows to skip: 1 (the CSV header row)
  6. Character set: UTF-8 (important for international customer names)
Step 9 — Assign Files (Step 8 in LSMW)
  1. Double-click "Assign Files"
  2. Assign source structure HEADER → to the file configured in Step 7
  3. This tells LSMW which file feeds which source structure (relevant for multi-file scenarios)
Step 10 — Read Data (Step 9 in LSMW)
  1. Double-click "Read Data"
  2. Click Execute (F8)
  3. LSMW reads the CSV and stores it in internal migration tables
  4. Check the status line: "500 records read, 0 errors" = success
  5. If errors: usually file not found, wrong separator, or encoding issue. Check file path and separator exactly.
  6. Go back to LSMW main screen — the "Read Data" step should now show a green checkmark
Always run Read Data in background (Schedule as background job) for files > 50K records to avoid dialog timeout. Use SM37 to monitor the background job.
Step 11 — Convert Data (Step 10 in LSMW)
  1. Double-click "Convert Data"
  2. Click Execute
  3. LSMW applies all field mapping rules and translation tables defined in Steps 5-6
  4. Review the conversion log — look for any "Conversion error" messages (e.g. unknown translation values, field overflow)
  5. Fix source data and re-read + re-convert until zero conversion errors
  6. After successful conversion, check a sample record: menu Goto → Converted Data → select record 1 — verify all fields are populated correctly

Step 12 — Start BAPI Processing (Step 11 in LSMW)
  1. Double-click "Start BAPI Processing" (this replaces "Create Batch Input Session" for the BAPI method)
  2. For the first test run: select "Foreground" mode with only 5 records — go to "From Record" = 1, "To Record" = 5
  3. Verify the 5 test customers in XD03 — check all 3 views (General, Company Code, Sales)
  4. If successful: run remaining records in Background mode
  5. LSMW writes a processing log — review it immediately after completion
Golden Rule: NEVER run the full file in foreground on first attempt. Always test 5–10 records first, verify in SAP, then run the rest in background. For cutover runs, split large files into batches of 50K and run sequentially to limit restart scope if a batch fails.

  ls_address-country     = ls_source-country.

  ls_company-recon_acct  = ls_source-akont.

    PERFORM log_error USING ls_source lt_return.
    ROLLBACK WORK.
  ELSE.
    " ⑤ Commit per record (or every N records for performance)
    CALL FUNCTION 'BAPI_TRANSACTION_COMMIT' EXPORTING wait = 'X'.
    ADD 1 TO lv_success_count.
  ENDIF.

Migration Load Order — 6 Steps

  1. Step 1 — General Data (KNA1): Load via XD01 using LSMW/BAPI with KTOKD, NAME1, LAND1, ORT01 — creates the client-level record. Must succeed before any subsequent views can be created.
  2. Step 2 — Company Code View (KNB1): Load FI company code data — AKONT (reconciliation account), ZTERM (payment terms), ZWELS (payment methods). Prerequisite: Company Code + GL Recon Account already exist.
  3. Step 3 — Sales Area View (KNVV): Load SD sales area data — VKORG, VTWEG, SPART, incoterms, pricing procedure. Prerequisite: Sales Organization structure fully configured.
  4. Step 4 — Partner Functions (KNVP): Load ship-to / bill-to / payer assignments. Prerequisite: All referenced customers (especially ship-to partners) must already exist in KNA1.
  5. Step 5 — Bank Details (KNBK): Load bank account details. Prerequisite: Bank Master (BNKA) must exist (run FI01 / bank load first).
  6. Step 6 — Credit Limits (KNKK): Load credit control area data and credit limits via FD32. Prerequisite: Credit Control Area configured (OB45) and customers loaded.

What & Why A Bill of Materials (BOM) defines the recipe for building a finished or semi-finished product — it lists every component (raw material, sub-assembly, or packaging item) and the exact quantity required. Without a correct BOM, MRP cannot calculate what to procure or produce, production orders cannot issue components, and product costing cannot roll up a standard cost.

BOM migration carries a high data quality risk: component materials must all exist in SAP before BOM items can be loaded. A single missing component will cause the entire BOM header to fail. The recommended approach is to load all raw material and component materials first, run a completeness cross-check (every STPO.IDNRK must exist in MARA), then load BOM headers. Volume can be deceptive — a company with 500 finished goods may have 15,000+ BOM line items once multi-level structures are expanded.

What & Why A Routing (also called a Task List) describes the sequence of manufacturing steps needed to produce a material — it defines which work centers perform each operation, how long each step takes (setup time, machine time, labor time), and in what order the steps must execute. From a migration standpoint, routings are often the most complex PP object to extract from legacy systems because many older MES/ERP systems store operations in non-standard formats. What & Why A Functional Location (FL) represents a permanent, physical position in a plant's structure — not a piece of equipment, but the place where equipment is installed. What & Why A Measuring Point is a defined monitoring location on a piece of equipment or functional location where periodic readings are taken — a pressure gauge on a pump, a vibration sensor on a motor, an hour meter on a generator, or an odometer on a vehicle. Measuring points enable counter-based and condition-based maintenance: SAP PM can automatically trigger a maintenance order when a counter reading exceeds a threshold (e.g. "service every 500 running hours" or "inspect when pressure exceeds 120 PSI").

Not all equipment needs measuring points — only equipment under a counter-based or condition-based maintenance strategy. Confirm with the PM functional lead which equipment categories require measuring points. The unit of measure on the measuring point must match exactly what will be entered in measurement documents (hours, kilometers, bar, rpm) — a mismatch here means counter readings will not trigger maintenance plans correctly.

What & Why A Measurement Document records the actual reading taken at a measuring point at a specific point in time — "Pump P-301 odometer read 4,850 hours on 15-Mar-2025." Measurement documents are the data that drives counter-based maintenance plan scheduling: SAP compares the current reading against the last service reading plus the interval to calculate when the next maintenance is due.

For migration, the only document that matters is the most recent reading as of the cutover date — this establishes the counter baseline so SAP schedules the next PM correctly. If this reading is missing or wrong, the maintenance scheduler will calculate incorrect next-due dates and either generate immediate work orders (if the counter appears overdue) or push maintenance far into the future (if the baseline is set too high). One measurement document per measuring point is the standard migration scope; loading the full history is rarely justified unless required by a regulatory body.
Config / Dependencies

  • Typically only the latest reading is migrated — establishes starting counter value
  • Historical readings generally NOT migrated (use archive reference only)

What & Why Open Maintenance Orders (Work Orders) represent maintenance activities that were in progress — either planned, scheduled, or partially executed — at the time of system cutover. These orders are what the maintenance team wakes up to on go-live day: they need to see their current workload in SAP, not have to look it up in the old system. A missing work order means a maintenance task falls through the cracks; an incorrectly migrated order causes confusion about what has already been done vs. what remains.

The scope decision is the same as for production orders: only truly open orders — released, in-progress, or pending — should be migrated. Completed and closed orders stay in the legacy system (or archive). For each open order, the key data is the equipment or FL it covers, the type of work, the planned labor and materials, the priority, and the planned dates. If some work has already been confirmed (partial labor hours or material issues), record the remaining work quantities — do not recreate confirmed actuals, as this would double-count costs in CO.
